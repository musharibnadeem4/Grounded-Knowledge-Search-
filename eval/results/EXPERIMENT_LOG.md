# EXPERIMENT_LOG

Decision rule (fixed in advance, TUNE set = 41 questions, 33 answerable): keep a change only if
(a) ctx_page_hit (gold page within the chunks `ask` hands the LLM; compare_runs.py --metric ctx) improves by >= 2
questions net (better - worse), OR answer accuracy (--metric answer) improves by >= 2 questions net;
(b) acl_leaks = 0; (c) warm retrieval latency increase <= 0.5 s; (d) all tests pass. Otherwise rejected
(flag stays default off). Each change is one flag. Baseline: `p4_baseline_tune` (retrieval), `p4_baseline_tune_answers`.
Hypotheses are written BEFORE the run; results are filled in afterwards (see "Results" below each id).

Baseline p4_baseline_tune: page_hit@5 0.606, @10 0.697, @20 0.848, MRR@10 0.334, askk_page_hit 0.697,
**ctx_page_hit 0.697 (23/33)**, ctx_gold_recall 0.601, ACL leaks 0, p50 80 ms.
Failure causes (inspect_run, 13 of 33 miss page_hit@5): 11 gold page at rank 6-50, 2 not in top 50; of 65 top-5
results 56 are the right filing but wrong page, 9 same company other filing, 0 other company. Typical: statement
rows whose label differs from the question wording (capex / Purchases of property, plant and equipment;
bottom line / net income; headcount / "employed N people") and MD&A narrative pages outranking the statement page.

**CORRECTION (bug found while analysing the budget; appended, earlier rows left in place).**
The first hybrid implementation returned `HYBRID_DEPTH` (50) fused hits instead of `k`, so `ask` read up to ~12
budget-limited chunks instead of ASK_K=8, and `search --k n` would have returned 50. Rank metrics at k <= 20
(page_hit@k, MRR) were unaffected, but the ask-depth metrics (askk/ctx) of `p5_x1_hybrid` and
`p5_x2_expand_on_hybrid` are INVALID (too generous) and rows X1 / X2b above are SUPERSEDED by the rows below.
Fixed in drg/retrieve.py (`n_out`), regression test `test_retrieve_hybrid_returns_k_hits`. Re-run as `p5_x1b_*`, `p5_x2c_*`.

**CONSTRAINT FOUND (affects all answer-level work).** (Provenance: the baseline answer run did not record its model; `openai/gpt-oss-120b` is inferred from .env being older than the run, Groq's 429 body and the cache keys.) Groq `openai/gpt-oss-120b` free tier: 8,000 tokens/minute AND
**200,000 tokens/day (rolling)**. Verified with a probe: "tokens per day (TPD): Limit 200000, Used 197041, Requested 5930.
Please try again in 21m23s". A full 41-question answer run (~37 LLM calls at ~3.4k tokens) costs ~125k tokens, so only
about 1.5 such runs fit per day. Consequences: (1) the p5_x2_answers / p5_x6_k12_answers runs I had queued were stopped
(they would have recorded "LLM unavailable" refusals once retries ran out; nothing was written to eval/results);
(2) an opt-in prompt-keyed LLM response cache (cache/llm) was added so unchanged prompts are never paid for twice, and it
was seeded from the raw responses already logged by the baseline run and the 13 finished questions of the stopped run;
(3) answer-level evaluation is reserved for the final configuration (Phase 6); X6 (ASK_K=12) and X7 (prompt v2) cannot be
evaluated at answer level today and are decided on retrieval evidence / left off by default.
